The catalogue was generated specifically for this run. `scripts/catalogue/seed.sql` in the repository was not used: it targets a superseded schema (it writes `vendor_status`, `latitude`, `longitude`, `is_active` and `offers.price`, and inserts no `vendors` row), so it fails on its first statement against the current migrations. It was left untouched.

Shape of the generated data, chosen so the queries do the work they would do in production:

* stores are clustered across 10 Tehran districts with a dense centre and a thinner edge, not scattered uniformly, so radius queries return realistic row counts
* only about 8000 of 40000 offer rows are eligible for display. The rest are expired, sold out, draft, paused, soft deleted, or belong to stores that are pending, suspended, rejected or deleted, so the `eligible_offers` view has to filter rather than scan a clean table
* favorites follow a heavy skew (a small number of very popular offers, a long tail with none), which is what the popular near you query counts over
* prices are spread with discounts between 32 and 70 percent, respecting the 30 percent floor that the `fn_offer_min_discount` trigger enforces from `platform_settings`
* titles and store names come from a repeated Persian vocabulary, so text search matches a realistic fraction of rows rather than none or all
* pickup windows are generated relative to the moment the test starts, with an evening weighting. This keeps the eligible set the same size whatever hour the test runs, which is a deliberate difference from production, where the eligible set shrinks late in the evening.

## Methodology

Two phases were measured, and they answer different questions.

**Phase A, realistic sessions.** 50 concurrent virtual users, each living through sessions the way the mobile app would drive them: an app open that issues the four home calls, then between 3 and 10 further actions, with log-normal think time between actions (median about 2.7 seconds, clamped to between 0.8 and 12 seconds). Arrivals were staggered over 10 seconds rather than starting together. Each user held one keep-alive connection and sent `Accept-Encoding: gzip`, reading every response body in full. About 40 percent of sessions were signed in (via the `X-Dev-User-Id` header, which is the authentication stand-in this build ships) and the rest were anonymous, because the `is_favorite` subquery only runs for signed in callers. Duration 180 seconds after a 30 second warmup that was discarded.

**Phase B, saturation.** The same request mix with the think time removed, at rising concurrency (10, 25, 50, 100), each level held for 45 seconds. This finds the ceiling and shows which component becomes the constraint.

Action weights within a session: browse the catalogue and scroll 35, open filters and filter 22, open a store and its offers 15, text search 13, map 10, saved offers 5 (signed in only). Every session begins with an app open, so the home endpoints carry the weight a real app gives them.

Latency was measured client side around the full request and response body read. It was cross checked against the server's own `latency_ms` field, which the API writes for every request, so application time can be separated from queueing and transport. Container CPU and memory were sampled every 2.0 seconds with `docker stats`, and PostgreSQL connection counts were sampled from `pg_stat_activity` over the same interval. Query plans were taken after the run with `EXPLAIN (ANALYZE, BUFFERS)` using the repository's own SQL sources, piped in over stdin so nothing had to be mounted or edited.

Not tested: authentication and OTP, vendor and admin routes, reservations, orders, writes of any kind, TLS, and any path that would change data.

**Endpoints this build does not serve.** Each endpoint was probed once before measuring. The following returned 404, meaning their routes are not registered in the running binary, so they were excluded from the workload and carry no results below: `GET /stores/{id}`. Treat their absence as a wiring defect to fix, not as a performance result.

## Findings

### 1. `GET /offers` is the slowest endpoint

Evidence: p50 39.2 ms, p95 70.6 ms, p99 127.7 ms over 2987 requests, against an overall p95 of 59.5 ms across all endpoints.

### 2. The distance filter cannot use the spatial index

Evidence: `home_popular_nearby` executes in 29.6 ms, `catalogue_search` with sort=nearest and a 5 km radius executes in 18.1 ms on the seeded dataset (plans in Appendix A).

The GIST index `idx_stores_location` does not appear in either plan. Both queries compute `fn_distance_m` as an expression and then compare the computed value, so PostgreSQL has no index it can use for the radius and falls back to evaluating every eligible row.

The plans contain a sequential scan, which is consistent with that reading.

### 3. Text search does not use the full text index

Evidence: the text search plan executes in 8.1 ms. The index `idx_offers_fts` over the generated `search_vector` column does not appear in the plan, and the trigram indexes do not appear.

`catalogue_search` matches with `e.title ILIKE $1 OR e.store_name ILIKE $1`. The `OR` across two tables inside a view generally prevents either trigram index from being used, and `ILIKE` never uses `idx_offers_fts`, which was built for `to_tsvector` matching. The index exists and is maintained on every write but is not read by this path.

### 4. Signed in requests pay for the is_favorite subquery

Evidence: the same catalogue query executes in 18.1 ms anonymously and 19.3 ms for a signed in user, a difference of 1.2 ms (6.5 percent).

The plan shows the `favorite_offers` lookup running once (`loops=1`), not once per row, so this difference is not per row subquery cost. On a single sample it is within run to run variation, and the anonymous plan additionally short circuits the subquery with a one time filter. Treat the gap as unexplained rather than attributed, and measure it over repeated runs before acting on it.

### 5. The database container is the busier of the two

Evidence during phase A: api averaged 3.0 percent CPU (peak 4.8) against a cap of 200.0 percent, and db averaged 66.6 percent CPU (peak 152.0) against a cap of 200.0 percent. Memory peaked at 31.6 MB for api and 233.9 MB for db.

The work is in the database, not in Go. Tuning the queries is where the improvement is, and adding API instances alone would not help.

### 6. Database connections are capped by the pgx pool defaults

Evidence: peak client connections to PostgreSQL by concurrency level: 10 users: 8, 25 users: 8, 50 users: 8, 100 users: 8.

`internal/infrastructure/repository/postgres/driver/pool.go` calls `pgxpool.NewWithConfig` without setting `MaxConns`, so the pool uses the pgx default of `max(4, runtime.NumCPU())`. The observed ceiling is 8 connections.

Connections stop rising while concurrency keeps climbing. Throughput by level: 10: 59.6/s, 25: 62.8/s, 50: 62.6/s, 100: 58.4/s. p95 by level: 10: 394.0 ms, 25: 691.9 ms, 50: 1300.6 ms, 100: 2609.3 ms.

The pool is not the binding constraint here, though. The database container ran at 197.0 percent CPU against a cap of 200.0 percent, so it was saturated at every level. Throughput is limited by database CPU, and raising `MaxConns` on its own would add contention rather than throughput. Treat the unset `MaxConns` as a correctness and portability problem (it silently follows the core count of whatever host the container lands on) rather than as the cause of this ceiling.

### 7. No failed requests

Evidence: all 5250 requests in phase A returned a 2xx status with no timeouts and no dropped connections.

## Recommendations

None of these were applied. The repository was left exactly as it was found.

1. Use `ST_DWithin` on the geography column for radius filtering instead of comparing a computed `fn_distance_m` value, and keep `fn_distance_m` only for presenting the distance of the rows that survive. This is what makes `idx_stores_location` usable.
2. Either search through `search_vector` with `websearch_to_tsquery` so `idx_offers_fts` is used, or split the `OR` into two indexable branches combined with `UNION`, so the trigram indexes can serve each side.
3. Set `MaxConns` explicitly in `driver/pool.go` (and `MinConns` for warm connections) rather than relying on `max(4, NumCPU)`, which silently depends on the core count of whatever machine the container lands on. Size it against the database's own `max_connections` and the number of API instances.

These are ordered by the size of the effect the measurements suggest, not by effort. Review them before acting: the measurements come from one host with synthetic data.

## Limitations

* Everything ran on one machine, so the load generator, the API and the database competed for the same CPU and memory. A production deployment separates them.
* The containers were capped (2 CPUs, 1g memory for the API, 2 CPUs, 2g memory for the database) to resemble a small staging VM. Numbers scale with those caps and are not a statement about production hardware.
* There is no network latency, no TLS termination and no reverse proxy in the path. Real clients pay all three.
* The dataset is synthetic. Its size and skew were chosen to be plausible, but real traffic has hot spots this generator does not reproduce, in particular repeated requests for the same popular stores.
* Pickup windows were generated relative to the start of the run, so the eligible set does not shrink through the evening the way it would in production.
* A real mobile client issues the four home calls in parallel. Each virtual user issued them sequentially on one connection, so app open wall time here is the sum rather than the maximum. Server side load per app open is identical either way.
* Authentication is the temporary X-Dev-User-Id header, not JWT. Once real token authentication lands, every request will additionally verify a token and reload the user, which this run does not measure.
* Redis was running but the public catalogue path does not use it, so its cost does not appear here.
